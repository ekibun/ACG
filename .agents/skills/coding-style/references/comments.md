# 注释：语言与格式（四种文件同一套）

**一套格式，`.kt` / `@Composable` / `.cpp` / `*.gradle.kts` 共用。**
标「基线」的是官方指南原文（出处见文末），「本项目」是本仓库叠加或**覆盖**的决定；冲突以「本项目」为准。

适用范围同 [`SKILL.md`](../SKILL.md)：**只管我们自己的代码** —— `cxx/ffmpeg/ffmpeg/`、
`cxx/quickjs/quickjs/`（上游 submodule）与 `cxx/webview/sdk/`（微软 SDK 头文件）**不在其中**。

## 一、语言：中文（本项目）

- **注释一律中文。**
- 但**标识符、路径、命令、任务名、报错与日志原文保持英文原样**，不要翻译 —— 翻成中文会变成
  "看着差不多"然后抄错（根 `AGENTS.md` 同款要求）。
- **术语不硬译**：`QuickJS`、`WebView2`、`JNI`、`dll`、`Modifier`、`dispatcher` 照写。
- 中文注释用**全角标点**（`，。；：`）；其中的代码片段、路径、符号用反引号包住、原样保留。
  —— 官方没有中文注释的规则，这条是本项目的补充。

## 二、形式：行注释 `//`（本项目统一）

| 用途 | 写法 | 不要 |
|---|---|---|
| 普通注释 | `// 说明`（`//` 后**一个空格**） | `/* … */` 块注释 |
| 多行说明 | 连续多行，**每行都带 `//`** | 拿 `/* … */` 拼一个块 |
| 行尾注释（C++） | 代码 + **两个空格** + `// 说明` | 用 tab 或竖排对齐 |
| 行尾注释（Kotlin / KTS） | 代码 + **一个空格** + `// 说明` | 两个空格 —— `ktlintCheck` 的 `standard:no-multi-spaces` 当场判失败 |

- **`/* … */` 只允许一处例外**：文档注释（下一节）。
- ⚠️ **别把这条当成 Google 的要求**：Google C++ 指南的原话是「**`//` 或 `/* */`，统一就好**」
  （`//` 更常用）—— 也就是两种都行。"只用 `//`"是**本项目**为了四种文件同形而定的，
  不是官方规则。**行尾空两格**倒是官方原话（§8.6「在行尾空两格进行注释」）。
- ⚠️ **但「行尾空两格」在 Kotlin / KTS 上做不到**（2026-09-19 实测）：`ktlintCheck` 的
  `standard:no-multi-spaces` 会把 `代码 + 两个空格 + //` 判成违规 —— 这是**工具强制**，不是口味问题。
  所以上表把 Kotlin / KTS 单列一档，行尾注释只用**一个空格**；C++ 没有这条 lint，照官方两空格走。
  （实测：加两格 → `:shared:ktlintCheck` 当场失败；改回一格 → 绿。违规点就在
  **代码与 `//` 之间**那一处。）
- **不做竖排对齐**：Kotlin 官方明确"避免任何形式的水平对齐"；Google 对**行尾注释**是**容许**
  对齐的（§8.6），但本项目不采用 —— 中文注释对齐更难看，而且四种文件要同一套。

### ⚠️ C++ 注释改完必须跑 clang-format —— 它会切开句子

根 `.clang-format` 是 `BasedOnStyle: Google` + `ReflowComments: true` + `ColumnLimit: 80`。
`ReflowComments` 会把中英混排的注释**合并成一个段落、再按列宽重填**，于是：

- 原来的行间断行被换成**一个空格** —— 句子被切开、句中凭空多出空格：
  `…两份不同的副本，` / `身份当场断掉` → `…两份不同的副本， 身份当场断掉`。
- 折行点可能落在**反引号代码段中间**：`` `a.b = ` `` / `` c; a.d = c` ``。

```sh
clang-format -i <file>...                # 先格式化
clang-format --dry-run --Werror <file>   # 干净才提交（pre-commit 只校验、不改文件）
```

**回修的正确姿势是「塌成一条物理行」**，不是逐处删空格：把被重排的段落写成一条长单行，
再跑 `clang-format -i`。此时没有「行间断行」可合并，它只按列宽折行，**不会**在句中插空格。
逐行删空格是徒劳的 —— 下一次 `-i` 会在旧断行处重新插一遍。

**判据**：`-i` 之后再跑一次，**diff 为空**即收敛（收敛时 `--dry-run` 必过）。
2026-09-20 实测：`quickjs.cpp` 首轮报 29 处违规，塌行后复跑 0 改动。

⚠️ **存量**：`cxx/quickjs/quickjs.cpp` 还有 3 处 2026-09-16 那次重排漏修的空格
（`， 别把` / `， 它得读到` / `。 以前这里`）。改到那几行时顺手修掉。

## 三、文档注释：`/** … */`（KDoc 形态，四种文件同形）

只给**对外契约、或"不读就会用错"的声明**写：

```kotlin
/**
 * 一句话说清它是什么、为什么是这个形状。
 * 第二段才写不显然的约束。
 */
```

- Kotlin 就是官方 KDoc。**C++ 与 Gradle KTS 用完全相同的形状**（`/**` 单独一行、后续每行 `*` 开头、
  ` */` 单独一行），这样四种文件看起来一致。
- **一句话能说清就用单行**：`/** 短说明。 */`
- **不写 `@param` / `@return` 标签**（Kotlin 官方建议把描述写进正文并链接参数）。
  本项目**不引入 Doxygen**，所以 C++ 也不用 `@brief` / `\param` 那一套。
- 分界：**文档注释**解释"这是什么、怎么用"；**普通注释**解释"为什么这么写"。两者都不复述代码在做什么。
  （「这是什么」指**契约与职责**，不是把标识符翻成中文 —— `/** 写播放倍速。 */` 配
  `fun setSpeedRatio` 是复述，该删。判据见[第六节](#六注释太长时怎么办)第一步。）
- **粒度**：Google 要求给**每个类**、**几乎每个函数声明**都写注释（§8.3 / §8.4）；
  **本项目不要求这个粒度** —— 只强制上面那两类，其余由改动者判断。注释比代码还长是不好的信号。
- **粒度按「是不是对外契约」分档**（2026-10-05 补）：`public` 的方法与类型是契约，写清用法与约束；
  **属性与 `private` 成员只写「不读就会用错」的那几条** —— 口径边界、陷阱、防误改的约束，
  「为什么长成这样」的推演一律不留。判据同[第六节](#六注释太长时怎么办)第一步：
  **把这句删掉，读者会不会用错？** 不会就删。
  信号是行数比：`val x: Int get() = …` 配 8 行 KDoc、`private var` 配 8 行推演，都属这一类。
  改一个文件时**整篇过一遍**，别只改手上碰的那一处。各档的参考行数见
  [第六节](#六注释太长时怎么办)的「长度基线」。

## 四、写什么、不写什么

- **写「为什么」与不显然的约束**，不写「代码在做什么」的复述。官方原话很重：
  「**永远不要**用自然语言翻译代码作为注释」「注释应当解释代码*为什么*要这么做和代码的目的」，
  并且「**要假设读代码的人 C++ 水平比你高**」（§8.6）。
  - 反例：`// 遍历列表` 配 `for (x in list)`。
  - 正例：`// 必须同步，否则 JS 侧会拿到已释放的 handle`。
- **写成完整句子**：正确的大小写、以句号结尾（官方 §8.7）。简短的行尾注释可以随意些。
- **不写会腐烂的信息**：`@author`、日期、"修改记录"。要追溯就看 git。
  （官方只讲"重大修改时**考虑**删掉原作者信息"，并没有禁止——所以这条是**本项目**的更严决定。）
- **不留注释掉的死代码**：删掉，git 历史里有。
- **不引用已经不在的东西**：注释里提到的类 / 函数 / 依赖，得能在**当前仓库或当前依赖树**里找到。
  一条依赖被整个移除后，注释里残留的「以前用的是 X」只会让人去仓库里翻一个不存在的东西 ——
  要么删掉这句，要么改成讲现状。例外：**明确写了「已删除 + 出处」的防回归说明**
  （如 `webview.cpp` 里的 `ScopedThreadInput`），那是刻意留的警告，不算过时引用。
- **待办写进根 [`TODO.md`](../../../../TODO.md)**（需要长期跟踪的）；代码里的临时标注写
  `// TODO: 中文说明`，不要派生 `NOTE` / `FIXME` / `XXX` 一堆前缀。
  （官方 §8.8 的形式是 `// TODO(身份): 说明`；本项目单人开发，省掉括号。官方那条本身很值得照抄：
  **`TODO` 写全大写**。）
- **注释与它说明的代码同级缩进**。

## 六、注释太长时怎么办

「注释比代码还长是不好的信号」这句话本身不可执行，但**它指的方向是对的**。
先按 §四 剔掉**复述**（「代码在做什么」的自然语言翻译，那种删了不看代码不受损失），
剩下的再问一句：「这几行是**约束**，还是在**讲机制**？」

### 第一步：先剔复述（§四 的那条重话）

判据：**把这行注释删掉，读者对代码的理解有没有变化？** 没变化 ⇒ 它在复述，删。

| 复述的样子 | 例子 |
|---|---|
| 把标识符逐个翻成中文 | `/** 写播放倍速。 */` 配 `fun setSpeedRatio(...)` |
| 复述类型 / 声明本身 | `/** 平台相关的视频输出区域。 */` 配 `expect fun VideoSurface(...)` |
| 复述控制流 | `/** 若为空则返回默认值。 */` 配 `?: default` |

⚠️ **这条要走在长度判断之前**。2026-10-05 漏过一次：当时只把注释分成
「约束 / 机制」两类，复述两类都不属于，于是被当成「不是机制 ⇒ 留」放过了。
**「不是机制」不等于「该留」。**

### 第二步：剩下的是约束还是机制

| 段落长什么样 | 处置 |
|---|---|
| 带实测数据（探针名、样本表、耗时区间、ffmpeg 源码行号） | **搬**进 `.agents/skills/` 下对应域的 `references/` |
| 在推演「为什么长成这样」（线程模型、生命周期推演） | **搬**，同上 |
| 纯语义的约束句（「必须 `cancel()` 不能 `close()`」） | **留**在原地 |
| 对外契约（签名、返回值含义、异常） | **留** |

约束本身**一个字都不能少** —— 搬走的是推演过程，不是约束本身。

⚠️ **「留」之前再问一遍「删了会怎样」**：只有约束与契约经得起这一问。
导航性说明（「哪部分归子类」）看着像信息，其实子类文件就在同目录，删掉无损。

### 搬去哪

落点是 `.agents/skills/` 下对应域的 `references/`（技能清单见 `AGENTS.md` §7）：

| 内容属于 | 搬到 |
|---|---|
| HTTP / 会话生命周期 / ktor 行为 | skill `project-traps` → `references/http-streaming.md` |
| 「不报错、只失效」的坑与实测症状 | skill `project-traps` → `references/silent-failures.md` |
| 挂死 / 崩溃 / 日志 / 判「阻塞在哪」 | skill `debugging` → `references/debugging.md` |
| JNI / native 构建 / 各库硬约束 | `cxx/AGENTS.md` 对应一节（那些是「不读就会改错」的**指令**，不是参考） |

正文留**一句裸约束 + 指到哪一节**。搬的时候顺手核一遍：被搬走的那段里有没有
「顺带提到的、别处没有的事实」—— 有的话补进落点文档，否则信息真丢了。

### 留在原地压短的情况

约束就贴在那个函数旁边、迁走就丢「在哪个函数上」⇒ 留下裸约束句，把推演过程删掉。
典型是 JNI 指针所有权那类（`Pointer` 的 KDoc 讲的是「哪一步必须同步」，搬走就没用了）。

### 长度基线（**建议性**，2026-10-05 实测）

**不是硬阈值** —— 按「尽量满足」执行。超了先按上面两步剔复述 / 搬机制；剔完还超，再问一句
「这段是不是**数据**（规则表、样例、状态机）而不是**解释**」—— 数据长是应该的。

量出来的惯例（animeko 2913 个 kt/kts：9374 个 KDoc 块 + 5824 个行内注释组；本机
`.workbuddy/ref/animeko` 可复算）：

| 注释位置 | 中位 | p90 | 建议上限 |
|---|---|---|---|
| 类 / 接口 / 对象 KDoc | 3 | 9 | **8 行** |
| 函数 KDoc | 3 | 7 | **6 行** |
| 属性 / 常量 KDoc | 3 | 5 | **5 行** |
| 构造参数 KDoc | 5 | 8 | 8 行 |
| **函数体内 `//`** | **1** | **2** | **2 行** |

函数体内那 4779 组里 83% 是单行、93% ≤ 2 行 —— **贴在代码旁边的解释天然只有一两句**；
写不下就是该搬进 `references/` 的信号。（animeko 最长那个 50 行组是**规则表**，长是因为它是数据。）

⚠️ 与下一节不冲突：那条反对的是**注释行 ÷ 代码行**（分母随文件大小漂移，算术必然）；
这里量的是**单个注释块的行数**，与文件大小无关，可以直接比。

### ⚠️ 别拿「注释行 / 代码行」当判据

**这个比例不能定阈值。** 分母是代码行 ⇒ 文件越短，密度越容易冲高，那是算术必然、
不是注释喧宾夺主。animeko（2026-10-04 实测，485 个主源码 `.kt`，已排除测试与构建脚本）：

| 代码行区间 | 文件数 | 中位密度 | 超 35% 占比 |
|---|---|---|---|
| 0–30 | 350 | 90.0% | **92.0%** |
| 30–60 | 50 | 73.0% | 62.0% |
| 60–120 | 32 | 27.1% | 21.9% |
| 120–300 | 28 | 25.3% | 21.4% |
| 300+ | 25 | 0.5% | 4.0% |

⇒ 它自己就有 92% 的小文件超 35%，拿 35% 当普适阈值是**把只在长文件上成立的观察
当成了规则**。（全量口径：animeko 注释/代码 = **14.5%**；代码行 ≥ 60 的文件上中位
10.5%、p90 35.7% —— 35% 只是那里的上界，不是判据。）

⚠️ **量的时候必须排掉 license header** —— animeko 每个源文件顶端的 GPL 头部有 200～377 行，
当成注释会把基线算歪。同理别拿「最长块」横比：animeko 看着最长的 240 行块是 GLSL 着色器脚本、
377 行是授权头，排掉之后它最长的常规 KDoc 是 61 行。
